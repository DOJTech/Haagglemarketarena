# Defensive security review (updated for v2.1; test data only, nothing run against production)
This is the author's own review. It is not a penetration test and does not show the system is "secure". **Nobody independent has reviewed this code**: see `REVIEW_BRIEF.md`.

| ID | Sev | Component | Finding | What changed in v2.1 | How it was checked | Remaining risk |
|---|---|---|---|---|---|---|
| SEC-01 | Med | Error handling | Stack traces on malformed JSON | Generic JSON error handler (v2.0) | `security.test.js` | Production-mode behaviour of the old code untested |
| SEC-02 | Low | Headers | `X-Powered-By` present | Header disabled (v2.0) | Header tests | None known |
| SEC-03 | Med | Display names | Duplicates, impersonation | Unique index, filter, blocked words (v2.0) | Names tests | Look-alike characters (capital I vs lowercase l) |
| SEC-04 | Med | Origin lock | API open to any site if `ALLOWED_ORIGINS` unset | **Production now refuses to start** without a valid `https://` list; malformed entries and `http://` also refused; trailing slash tolerated | `test/harness/wiring.test.js` (ran, passes) | This only stops OTHER WEBSITES using visitors' browsers. A script can send any `Origin` header, so it is **not** protection against bots |
| SEC-05 | Low | Privacy | Third-party font host | Removed (v2.0) | Host scan | None |
| SEC-06 | Med | Identity | Device ID was the only credential | **Accounts** (username + password, scrypt-hashed, salted). A player with an account needs a session token (stored only as a hash, 14 days, max 5 per account) for every action; the device ID alone is refused | Wiring tests (ran, pass); `test/accounts.test.js` against real Postgres (**written, not run**) | Players without an account are still device-ID-only (practice only). Registering claims an existing device ID, so if an ID leaked before its owner registered, the first to register wins. No password reset (no email or phone). Session token sits in browser storage like the device ID did; CSP is the defence against script injection |
| SEC-07 | Med | Ranking | Fake devices claimed ranked slots | **Ranked play needs an account.** Account creation capped per network (default 20/day) and overall (default 300/hour); creation of new device records capped per network (default 200/hour). Existing ranked limits kept (1 per account per day, 3 per network, 60 s minimum) | Wiring tests (ran, pass) | **Still open:** nothing proves an account is a real person. Someone with many addresses can still make many accounts, more slowly. Real protection needs a verified phone or email (needs a provider and your choice). Per-network caps also hit real players on shared mobile networks, so tune them against real traffic |
| SEC-08 | Low | Rate limits | In memory, one server, per address only | Sensitive actions (register, login, owner login, start game, new devices) are now counted **in the database**, so limits are shared by every server instance and survive restarts, and are also counted **per username and per player**, not only per address. The coarse in-memory limiter remains for general traffic | Unit tests for the limiter (ran); wiring tests (ran); real SQL only in `accounts.test.js` (**not run**) | The coarse limiter is still per server and bypassable with many addresses. No protection against network-level floods: that needs a provider in front (for example Cloudflare or your host's DDoS tier) |
| SEC-09 | Med | Owner access | One shared key, no second factor | Owner signs in with key **and** a one-time code from an authenticator app (TOTP, RFC 6238). Each code works once. Result is a 30-minute session token; the key is no longer kept in the browser or sent on every request. Lockout after 5 failures per address. **Production refuses to start without `ADMIN_TOTP_SECRET`.** Owner actions go in an audit log (`/api/admin/audit`) | TOTP checked against the official RFC 6238 test vectors (ran, pass); wiring tests incl. replay, lockout, expiry (ran, pass) | The key and the TOTP secret both sit in Render's environment: anyone who controls your Render account has both. Protect that account with two-factor sign-in. One shared owner identity, no per-person accounts. Failing 10 times locks a known username for 15 minutes (accepted trade-off) |
| SEC-10 | Low | CSP | Inline styles allowed | Unchanged | n/a | Open |
| SEC-11 | Info | Dependencies | `npm audit --omit=dev`: 0 known vulnerabilities when last run in v2.0 | **No new dependencies added** (new code uses only Node's built-in `crypto`) | **Not re-run** (no network access when this was prepared) | Re-run `npm audit --omit=dev` before release |
| SEC-12 | Med | Database TLS | `rejectUnauthorized:false`: the server does not verify the database's certificate | New setting `DB_SSL_STRICT=1` verifies it. Off by default so an untested change cannot stop your deploy | Not tested against your host | **Open until you turn it on** and confirm the site still connects |
| SEC-13 | Med | Denial of service | Slow-connection and resource exhaustion | Request header timeout 15 s, request timeout 30 s; database connect, query and statement timeouts; idle-connection error handler; password hashing limited to 3 at once with a queue cap; `/healthz` rate limited; in-memory tracking pruned | Reviewed and partly unit-tested (hashing gate). **No load or DoS test was run** | Real resilience is unmeasured. Test on a staging copy with your host's permission |

## Checks run for this update (Node 22, Linux, no database)
| Suite | Result | What it does and does not prove |
|---|---|---|
| `test/security.unit.test.js` | 10 of 10 pass | TOTP vs RFC 6238 vectors, password hashing, tokens, rate-limit logic, concurrency gate |
| `test/harness/wiring.test.js` | 21 of 21 pass | The real `server.js` routes, run against a **fake in-memory database**: owner login, replay and lockout, accounts, sessions, ranked gating, limits, startup refusals. I also broke the code five ways on purpose and confirmed these tests failed each time. It does **not** prove the new SQL is valid on Postgres |
| `test/engine.unit.test.js` | 28 of 28 pass | Unchanged game engine |
| `test/accounts.test.js` | **Not run** | Written to run every new SQL statement against a real local Postgres. **Run it first** |
| `security`, `anticheat`, `features`, `moderation`, `campaigns`, `load`, `browser` suites | **Not run** | Need Postgres. The first five were edited for the new owner login and for `RANKED_NEEDS_ACCOUNT=0`. The earlier "58 checks" in `security.test.js` are from v2.0 and are not re-confirmed. The browser suite was not updated for the new account box |

## Not tested
Real Postgres with the new code, production deployment, TLS settings, account security at GitHub, Render, Netlify and your database host (turn on two-factor sign-in on each), denial-of-service, anything beyond 30 simulated players, supply-chain attacks, database backups and restores, real devices.
